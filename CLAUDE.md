## What this is
Remote grave-care marketplace for Turkey (İstanbul pilot, Turkish diaspora in Europe). Customer orders periodic grave care; a vetted caretaker uploads GPS/timestamp-verified before/after photos; customer approves; only then is payment released. **Turkish-only UI** (MVP1; i18n layer deferred), calm/respectful tone.

**Status: Turborepo monorepo, backend build in progress.** `apps/api` has a full Prisma schema/migrations/seed (spec §4), a working auth module (spec §6), the full spec §5 API surface (orders/payments/subscriptions/partners/cemeteries/kpi/grave-locations) with Idempotency-Key support, the order lifecycle state machine (spec §21.2) with BullMQ-driven SLA automation, **real payment integration via iyzico** (spec §3/§7, not Stripe — see the Payment provider section), and the **evidence verification system (spec §8)** — real S3 Object Lock/WORM (directly confirmed active, `ObjectLockMode: "COMPLIANCE"`), real EXIF/GPS/Haversine checks, ADIM 7 fully done and verified. `apps/web`'s **order wizard (`siparis/page.tsx`, including the real payment step) and a new login/register page (`giris/page.tsx`) are now wired to this real API** — see the Frontend wiring section below. The **panel (`panel/page.tsx`) is still hardcoded/simulated by design** (out of ADIM 5's scope, see that section). **`apps/field-pwa` (Saha Mobil WebApp, spec §12) is new — ADIM 8's online-only scope is done and live-verified** (login → task list → task detail → camera capture → complete, real S3 staging bucket, see the Field partner PWA section), **and ADIM 8b (offline-first, spec §12.2) is now done and live-verified too** — unified IndexedDB action queue (start/evidence/complete), Service Worker with SPA offline-navigation fallback, three independent reconnect triggers (Background Sync, `online` event, a 20s periodic poll added after a real gap was found live-testing), see the Field partner PWA offline-first section. **Admin Panel (`apps/admin`, spec §11, ADIM 9) is now fully done** — all 7 spec §11.1 modules (Partner Yönetimi, Sipariş Yönetimi, Atama Ekranı, Şikayet Yönetimi, Kullanıcı & Rol Yönetimi, Mezarlık & İzin Yönetimi, KPI Dashboard) built and live-verified across 9 phases, including resolving the previously-tracked field-partner onboarding→active blocker and the first real iyzico refund implementation — see the Admin Panel section below for the full per-phase history and the real gaps found and fixed along the way.

## Database (apps/api/prisma)
- `schema.prisma` implements spec §4.1–4.8 literally: table/column names via `@map`/`@@map` (snake_case, matches spec exactly), enum values verbatim, §4.8 indexes. One deliberate exception: `audit_log` has no `updated_at`/`deleted_at` — spec §4.7 calls it "immutable, append-only", which is incompatible with the general soft-delete/update convention every other table follows.
- PostGIS: `grave_locations` needs a GIST index on a geography point per spec §4.8. Prisma's schema DSL can't express a PostGIS generated column, so it's a second raw-SQL migration (`prisma/migrations/20260101000001_grave_location_geography`) layered on top of the Prisma-managed base migration.
- **Resolved spec gap:** the field partner's task-completion note ("saha notu", max 200 chars — spec §8.2/§12.1/§17) had no column anywhere in spec §4's table list. User decision: `evidence_photos.field_note` (nullable `VARCHAR(200)`, migration `20260101000002_evidence_photo_field_note`) — matches spec §8.1's "note sent along with the evidence upload", not a new `orders` column, no junction table.
- **`grave_locations.section`/`.plot` are nullable** (migration `20260101000004_grave_location_section_plot_nullable`, user decision, ADIM 5) — the wizard's "ada/parsel bilmiyorum, yardım isteyin" path only requires a `cemeteryId`; section/plot are genuinely `NULL` until a field partner or ops/admin fills them in later via `PATCH /grave-locations/:id` (see API Layer section), matching the same "filled in later" pattern spec already uses for `lat`/`lng` on the same table. No placeholder/sentinel strings are ever written.
- **Fixed a real bug found via live end-to-end testing, not a hypothetical:** `prisma/seed.ts`'s four cemetery IDs (and the seed grave-location/subscription IDs) were originally non-RFC4122 placeholders like `00000000-0000-0000-0000-000000000001` — the version nibble isn't `1`-`5`, so `class-validator`'s `@IsUUID()` (used on every DTO field referencing them, e.g. `CreateGraveLocationDto.cemeteryId`) rejects them outright. This never showed up in the e2e test suite (tests create their own real `@default(uuid())` fixtures), only when the actual wizard flow was driven end-to-end against seeded data. Fixed by reshaping every seed ID to a valid v4 form (`00000000-0000-4000-8000-...`) — still readable/sequential, now passes validation.
- No live Postgres+PostGIS is available in this sandbox. The schema/migrations were still verified for real: applied end-to-end (all 12 tables, FKs, indexes) plus a full seed run against a temporary embedded Postgres — only the PostGIS extension itself couldn't be exercised there. Before relying on the PostGIS migration in a real environment, run `npm run db:deploy --workspace=apps/api` against actual Postgres 16 + PostGIS to confirm it.
- Local dev: copy `apps/api/.env.example` to `apps/api/.env`, point `DATABASE_URL` at a real Postgres 16 + PostGIS instance, then `npm run db:deploy --workspace=apps/api && npm run db:seed --workspace=apps/api`.
- **`npm install`/`npm ci` at the repo root does NOT reliably run `apps/api`'s own `postinstall` (`prisma generate`)** — this is a known npm-workspaces quirk (nested workspace `postinstall` scripts don't consistently fire from a root install). Fixed by adding `postinstall` to the **root** `package.json` that explicitly delegates to `apps/api`'s. If `@prisma/client` types ever look stale/missing after an install, run `npm run postinstall --workspace=apps/api` (or `npx prisma generate` inside `apps/api`) manually. When checking whether the client is actually generated, look at `apps/api/node_modules/.prisma/client/index.d.ts` — **not** `apps/api/node_modules/@prisma/client/index.d.ts`, which is always a 1-line re-export stub by design.

## Auth (apps/api/src/auth) — spec §6
- `POST /auth/register`, `/auth/login`, `/auth/refresh` per spec §5's exact paths. Register only allows self-registerable roles (`customer`, `field_partner`) — `ops_manager`/`support_agent`/`admin` can never be created through this endpoint.
- argon2id password hashing (min 10 chars, spec §6.2). Access token: JWT, 15 min. Refresh token: JWT, 7 days, **httpOnly + Secure + SameSite=Lax cookie** (path-scoped to `/api/v1/auth`).
  - **Why Lax, not None:** no hosting/domain architecture has been decided yet (see Workflow section — no deploy integration exists). The natural default for this split (SPA + API) is same registrable domain via subdomains (e.g. `app.guzelkabir.com` + `api.guzelkabir.com`) — SameSite compares registrable domain, not host/port, so those *are* same-site, and so is `localhost:3000` ↔ `localhost:3001` in dev (port isn't part of the site definition either). Lax works in both cases and, unlike None, actually blocks the cookie from attaching to cross-site POST requests — real CSRF protection, not just "works everywhere." If a genuinely separate registrable domain gets chosen later (ADIM 13 infra step), revisit this: either front both with a reverse proxy to stay same-site, or upgrade to `None` + a real CSRF token (spec §14.3) — don't silently leave it at Lax in that scenario, it would break the cookie entirely, not just weaken security.
  - `CORS_ORIGIN` env var controls allowed origins (`credentials: true` required for the cookie to be sent).
- **CSRF token (spec §14.3, "form tabanlı işlemlerde") — deliberately deferred to ADIM 9, not silently skipped.** Interim risk is low: every `Authorization`-header-protected endpoint is CSRF-immune by construction (browsers won't auto-attach a Bearer header cross-site), and the one cookie-authenticated endpoint (`/auth/refresh`) is already covered by `SameSite=Lax` (blocks the cookie on cross-site POST). Revisit together with the general rate-limiting hardening (§14.3) in ADIM 9.
- **Refresh rotation + reuse detection**, backed by Redis (`refresh:current:<userId>` → current valid `jti`, TTL 7d): every refresh both validates and replaces the stored `jti`. Presenting an already-rotated-away token is treated as a stolen-token signal and revokes the session outright (deletes the Redis key), not just rejects that one request.
- **Known simplification, not in spec, worth revisiting:** single active refresh session per user (one Redis key per user, not a set). Logging in on a second device invalidates the first device's refresh token. Fine for MVP1; if multi-device sessions are needed later, change the Redis key to a per-`jti` set instead of a single current-jti value.
- **`login()`/`refresh()` now reject soft-deleted (`deletedAt`) users** — fixed in Admin Panel ADIM 9 Phase 7 (see that section), when "deactivate a staff account" first gave `deletedAt` a real writer and this previously-invisible gap became exercisable. A still-valid **access** token (max 15 min left) is accepted as a bounded, standard JWT tradeoff — not fixed, deliberately.
- RBAC: `JwtAuthGuard` is wired as a **global** guard (`APP_GUARD` in `AppModule`) — every route is protected by default; use `@Public()` to opt out (see `AppController.getHealth()`). `@Roles(...)` + `RolesGuard` (also global) encode spec §6.1's role matrix — apply `@Roles('ops_manager', 'admin')` etc. on new endpoints as they're built.
- Login is rate-limited 5 attempts / 15 min, keyed on IP **+** attempted email (spec §6.2) — see `LoginThrottlerGuard`. The general 100 req/min/IP limit (spec §14.3) is deferred to the security-hardening step (ADIM 9).
- **Deferred to later steps, not yet implemented:** per-access audit logging on sensitive fields (`deceased_name`, `national_id_encrypted`, spec §6.2/§14.1 — spans multiple resource modules, not just auth). The field-partner KYC gate itself is done — see the API Layer section below.
- **⚠️ Redis logic is NOT yet verified against a real Redis instance.** No real Redis was reachable in the sandbox this was built in (network egress to the download source was blocked), so `REDIS_CLIENT` was overridden with `ioredis-mock` for testing — it faithfully emulates ioredis's command surface, so the rotation/reuse-detection *logic* genuinely ran, but the transport was never a real Redis server/process. **Before pilot launch, `apps/api/test/auth.e2e-spec.ts` must be re-run against an actual Redis instance** (drop the `ioredis-mock` override) to confirm — same standard as the PostGIS caveat above, don't skip it.
- Tests: `apps/api/test/auth.e2e-spec.ts` (Jest + Supertest) covers registration validation/role-restriction, login failure, the full rotate→reuse-detect→session-revoked chain, and the rate limiter. Not wired into CI yet — needs a real Postgres, which lands with Testcontainers in ADIM 9 (spec §13.2/§15). Run locally: `DATABASE_URL=... JWT_ACCESS_SECRET=test JWT_REFRESH_SECRET=test npm run test:e2e --workspace=apps/api` against a migrated Postgres.

## API Layer (apps/api/src/{orders,payments,subscriptions,partners,cemeteries,kpi}) — spec §5

All endpoints from spec §5's table are implemented with the exact paths/methods/roles specified, in dedicated one-module-per-resource NestJS modules.

**Idempotency-Key** (spec §5.1, `src/common/idempotency`): a global `@Idempotent()` decorator + Redis-backed interceptor (`IdempotencyInterceptor`, registered as `APP_INTERCEPTOR`). Header is optional per-request (client chooses to send it, like Stripe's own API) — when present, a repeat request with the same key/user/route returns the cached first response instead of re-executing; a concurrent duplicate in flight gets `409`. Applied to `POST /orders`, `POST /payments/intent`, `POST /subscriptions` — spec §5.1 literally names only "ödeme ve sipariş oluşturma" (payment + order creation); subscription creation was added too since it's the same class of double-submit risk, not a literal spec requirement.
  - Tested against real Postgres on all three routes: `orders.e2e-spec.ts` and `misc.e2e-spec.ts` both do a full success-path dedup check (same key → same created id → exactly one DB row) for `/orders` and `/subscriptions`. `/payments/intent`'s success path can't be exercised the same way (calls the real Stripe SDK, no real Stripe test key in this sandbox — see the API Layer section) — what's tested there instead is that a failed attempt doesn't poison the cache: retrying with the same key gets a fresh honest failure, not a stuck `409` from an abandoned lock and not an incorrectly-cached success.

**Field-partner KYC gate** (`OrdersService.assign`, spec §6.2/§17): a plain service-layer check, not a DB trigger, per explicit instruction — assigning to a `FieldPartner` whose `status !== 'active'` throws a `ForbiddenException` with a specific message ("kimlik doğrulama, sabıka kaydı ve sözleşme imzası tamamlanmadan görev ataması yapılamaz"), not a generic 403. Verified end-to-end in `test/orders.e2e-spec.ts` against a real Postgres: rejected while `status='onboarding'`, succeeds once flipped to `'active'`.

**Stripe webhook signature verification** (`PaymentsService.handleStripeWebhook`, spec §5.1): `Stripe-Signature` header verified via `stripe.webhooks.constructEvent()` against the **raw request body** — `main.ts` disables Nest's global body parser and manually routes only `/api/v1/payments/webhook` through `express.raw()`, everything else through `express.json()` (a single branching middleware, not two competing ones — two separate un-scoped body parsers would double-consume the request stream). Verified event IDs are recorded in `processed_webhook_events` (new table, not in spec §4 — spec §5.1 requires it explicitly, so this isn't a gap needing a decision, unlike `field_note`); replayed events return `200 {duplicate: true}` without reprocessing. All of this — missing signature, invalid signature, valid signature + processing, and replay — is verified for real against Postgres in `test/payments.e2e-spec.ts`, including generating a genuinely valid signature locally via `Stripe.webhooks.generateTestHeaderString()` (pure HMAC math, no live Stripe API needed).
  - **Gotcha if you touch these tests:** supertest's `.send(Buffer)` silently JSON-serializes the Buffer object itself (`{"type":"Buffer","data":[...]}`) when a `Content-Type: application/json` header is set — it does NOT send raw bytes. This corrupts the payload and breaks signature verification in a confusing way (looks like a signing bug, isn't one). Use `.type('json').send(rawString)` instead — that's confirmed to preserve the exact bytes end-to-end.
  - **ADIM 4 note, since superseded by ADIM 6:** `POST /payments/intent` originally called the real Stripe SDK; this sandbox had genuine network egress to Stripe's API (confirmed via a real `StripeAuthenticationError` 401), but no real Stripe test key, so the success path couldn't be exercised — same shape of gap now applies to iyzico instead, see the Payment provider section for what's actually implemented today.

**`grave-locations` module (`src/grave-locations`, spec §5's table has no route for this at all — user decision, ADIM 5):**
- `POST /grave-locations` (`customer`, `ops_manager`, `admin`) — find-or-create by `(cemeteryId, section, plot)`. Dedup only applies when both `section` and `plot` are provided; the "yardım isteyin" path (neither given) always creates a fresh row, since there's no natural key to dedup against and merging distinct "needs field detection" requests into one row would be actively wrong.
- `PATCH /grave-locations/:id` (`ops_manager`, `admin`, `field_partner`) — fills in `section`/`plot`/`lat`/`lng` once a field partner locates the grave in person. Role-gated only, no ownership check tying the partner to a specific order/location (matches the exact scope the user asked for — "sadece ... rolü ... doldurabilsin"); revisit if this ever needs tightening to "assigned partner only."
- Tested against real Postgres (`test/misc.e2e-spec.ts`): dedup vs. always-fresh-row behavior, `403` for a customer hitting `PATCH`, `404` for a nonexistent id.

**`users` module (`src/users`, spec §5's table has no route for this either — user decision, ADIM 5):**
- `GET /users/me` — no `@Roles()` (any authenticated user, RolesGuard passes through when no roles are set); returns the caller's own `{id, email, fullName, phone, role, locale, isVerified, kycStatus}` (never `passwordHash`), looked up by `user.sub` from the JWT. Added specifically because `apps/web`'s `AuthProvider` had no server-verified source for `fullName` — the JWT only carries `{sub, role}` — so the displayed name reset to a placeholder on every full page reload. Not a new architectural call: a direct, natural complement to spec §6's RBAC/auth design.
- Tested against real Postgres (`test/auth.e2e-spec.ts`): `401` unauthenticated, `200` with the correct `email`/`fullName`/`role` and no `passwordHash` leak.

**Judgment calls made without stopping to ask — flagged here per usual practice, not silently decided:**
- **`GET /orders` scoped to `Customer` too, not just `Ops/Admin`** (spec's literal role column says "Ops/Admin"). Without this, apps/web's panel has no endpoint to list "my orders" at all. Customers can call it but results are hard-scoped to their own `customerId` server-side (they cannot override the filter). If this reading is wrong, tell me and I'll split it into two endpoints instead.
- **`POST /orders/:id/evidence` implemented as a JSON metadata-registration endpoint, not literal multipart file upload.** Spec §5 calls it "multipart", but spec §8.1 says photos upload directly from client to S3 via pre-signed URL, never proxied through the backend — the two descriptions contradict each other, and S3/pre-signed-URL infra doesn't exist yet (that's ADIM 7). This endpoint currently just records `{photoType, fileUrl, exifGps*, fieldNote}` for a URL the client is assumed to have already uploaded elsewhere. Revisit when ADIM 7 builds the real upload flow.
- **`field_partners.national_id_encrypted` is genuinely AES-256-GCM encrypted now** (`src/common/crypto/national-id.crypto.ts`), not left as a TODO — storing a raw TC kimlik no in a column named `_encrypted` would be an active bug, not just "not hardened yet." The key itself comes from `KMS_KEY_ID_PII` treated as a raw symmetric secret (hashed with SHA-256 to get 32 bytes) — there is no real KMS behind it yet; that's still ADIM 9's job. Don't mistake "encrypted at rest" for "properly key-managed."
- **✅ RESOLVED (Admin Panel ADIM 9, Phase 1): `POST /partners/:id/approve`/`POST /partners/:id/reject` now move a field partner between `onboarding`→`active`/`rejected` for real.** Previously a known, tracked blocker (spec §11.1 mentions "onboarding onay akışı" but spec §5's endpoint table had no route) — see the Admin Panel section below for the full implementation. Backend done and e2e-verified; the `apps/admin` frontend screen for this lands in Phase 4.
- **`GET /kpi/dashboard`** returns only what's honestly computable from the current schema (orders-by-status, AOV, total revenue, complaint rate) — `conversionFunnel`, `repeatCustomerRate`, `averageSlaHours` are `null`. Spec §11.1's funnel/SLA metrics need event-tracking infrastructure that doesn't exist yet (Admin Panel's job); nothing was fabricated to fill the gap.

Tests: `test/orders.e2e-spec.ts`, `test/payments.e2e-spec.ts`, `test/misc.e2e-spec.ts` (cemeteries/kpi/partners/subscriptions) — all Jest + Supertest against a real (temporary, embedded) Postgres, same not-in-CI-yet caveat as auth's tests. `test/test-app.helper.ts` centralizes the app-bootstrap boilerplate (raw-body routing, Redis mock, JWT minting for test fixtures) shared across all four e2e spec files.

## Payment provider: iyzico, not Stripe (spec §3/§7 updated — ADIM 6, implemented)

**Spec §3's "Ödeme: Stripe (birincil), PayPal (opsiyonel diaspora için)" is superseded — user decision, stated rationale:** Stripe does not open production merchant accounts for companies incorporated in Turkey (only Stripe's test/sandbox mode is geography-unrestricted); GüzelKabir's operating company is Turkish, so real money could never actually move through Stripe here. PayPal has the identical Turkey-incorporation restriction, so it's dropped too — not merely deprioritized as "opsiyonel," it's out. **New primary (and only) provider: iyzico** — Turkey-headquartered, TRY-native, 3D Secure built in, PCI DSS SAQ-A compliant, and — unlike Stripe/PayPal — actually issuable to a Turkish company.

**This is a payment-vendor swap, not a business-rule change.** Spec §7's actual rules — 3D Secure mandatory, capture the customer's payment immediately on success, release payout to the field partner only after customer approval (48h window; see Order State Machine below), refund/chargeback handling, multi-currency for diaspora customers — are unchanged. Only the vendor and its API shape change. One clarification worth stating explicitly since it shapes the whole mapping: **spec §7.1's "onaylandıktan sonra ödeme" framing is about the payout to the *field partner*, not about withholding the *customer's* charge** — re-reading spec §2.3 madde 3 and 7 confirms the customer's card is captured in full the moment `payment_intent.succeeded` fires (order → `confirmed`), and the `partner_payouts` record (platform → caretaker) is what's actually gated on the 48h approval window. This means iyzico's standard immediate-capture flow is a direct architectural match — no PSP-level authorize/capture split is needed (iyzico does have a pre-auth/"ön provizyon" feature if that were ever needed, but the existing Stripe implementation never used one either, so parity doesn't require it).

ADIM 4's Stripe integration (`PaymentsService`, webhook raw-body routing in `main.ts`, `processed_webhook_events` table, e2e tests) was the reference architecture — ADIM 6 replaced it piece-by-piece with iyzico's equivalents below, not a rewrite from scratch (`iyzipay` on npm, iyzico's own officially-maintained Node.js SDK):

| Spec §7.1 / current Stripe concept | iyzico equivalent |
|---|---|
| `stripe.paymentIntents.create()` | Checkout Form initialize — `POST /payment/iyzipos/checkoutform/initialize/auth/ecom`. Returns a `token` + `checkoutFormContent` (a Base64 HTML/JS snippet embedded directly in the page — same PCI DSS SAQ-A story as Stripe Elements, card data never touches our backend) or a `paymentPageUrl` for a hosted-redirect alternative. |
| Stripe.js client-side automatic 3DS | 3D Secure runs inside the embedded Checkout Form itself — no separate client SDK call needed, same "card data never touches us" guarantee. |
| `client_secret` returned to the frontend | `checkoutFormContent` / `paymentPageUrl` + `token` returned to the frontend. |
| Stripe webhook (`payment_intent.succeeded`, `Stripe-Signature` header, HMAC verified against the **raw request body**) | iyzico webhook (event type `CHECKOUT_FORM_AUTH`, `status: SUCCESS\|FAILURE`, `X-IYZ-SIGNATURE-V3` header, HMAC-SHA256 verified against **named JSON fields**: `secretKey + iyziEventType + iyziPaymentId + token + paymentConversationId + status`, concatenated in that exact order, hex-encoded). **ADIM 6 simplification, not just a swap:** since iyzico's signature is computed from parsed field values rather than raw bytes, `main.ts`'s current `express.raw()`-vs-`express.json()` branching middleware (built specifically for Stripe's raw-body requirement) becomes unnecessary — the webhook route can go back to plain `express.json()` like every other route. |
| *(no direct equivalent used today)* | iyzico also delivers a synchronous `callbackUrl` POST (the customer's browser redirects there with `token` right after completing payment) *and* a pull-based `POST /payment/iyzipos/checkoutform/auth/ecom/detail` (query by `token` for the authoritative result) — an independent second confirmation path on top of the webhook. Worth using as a belt-and-suspenders check, same spirit as the existing idempotent `processed_webhook_events` replay-guard. |
| Stripe Radar risk score (spec §7.3: ">75 risk skoru → manual inceleme kuyruğu") | iyzico's built-in fraud engine returns `fraudStatus` on the payment/retrieve response: `1` (approved) / `0` (needs manual review) / `-1` (rejected) — a simpler 3-state model than a numeric threshold, but the same manual-review-queue behavior spec already describes. |
| Stripe Refunds API (spec §7.3) | `POST /payment/refund` — refunds keyed on `paymentTransactionId` (**note: per-basket-item granularity, not per-order/PaymentIntent like Stripe**). **✅ Actually implemented, Admin Panel ADIM 9 Phase 6** — `PaymentsService.refund()`, see the Şikayet Yönetimi section. This row previously described the mapping only; the real method didn't exist until Phase 6, and the row's wording didn't make that distinction clearly enough at the time. |
| Stripe Billing (subscriptions, spec §7.2) | iyzico's own Subscription API (`docs.iyzico.com/en/products/subscription`) — separate initialize/cancel/retry-failed-charge endpoints keyed on a `subscriptionReferenceCode`, not an invoice-driven model like Stripe Billing. **The biggest structural difference, not just a rename** — expect real service-layer changes here when ADIM 6 reaches §7.2, not a 1:1 swap. |
| Stripe automatic multi-currency (spec §7.3, EUR/USD/GBP diaspora support) | iyzico's "Multi Currency" feature (USD/EUR/GBP/RUB/CHF/NOK — covers everything spec needs) — but it's an **opt-in paid add-on** on the iyzico merchant panel (99 TL/yr as of this research), not on by default like Stripe. Settlement always lands in TRY at the CBRT rate on the transaction date, which already matches spec §7.3's "fiyatlandırma TRY bazlı sabitlenip günlük kur ile senkronize edilir" — no pricing-model change needed. |
| `STRIPE_SECRET_KEY` (Bearer auth) | `IYZICO_API_KEY` + `IYZICO_SECRET_KEY` + `IYZICO_URI` (sandbox: `https://sandbox-api.iyzipay.com`, production: `https://api.iyzipay.com`). iyzico signs each individual API *request* (an `IYZWSv2` HMAC scheme, Base64) — handled transparently by the official `iyzipay` SDK, same as how the `stripe` npm package hides Stripe's Bearer-token mechanics today. **Same handling protocol as before, carried forward unchanged:** the user adds their own real iyzico sandbox/production keys to `apps/api/.env` directly, not shared with the assistant. |

**Explicit tradeoff, resolved (user decision):** spec §20.2's risk table names "Stripe + PayPal çift entegrasyon, devre kesici (circuit breaker) deseni" against payment-provider outages. Since PayPal has the same Turkey-incorporation problem as Stripe, that dual-provider redundancy isn't achievable with a Turkey-incorporated company. Two options were weighed: (1) add PayTR as a second Turkish PSP now and build a real circuit breaker — preserves spec §20.2's original redundancy intent, but doubles ADIM 6's integration surface for a pilot that doesn't need it yet; (2) accept single-provider (iyzico-only) risk for MVP1, document it as a deferred MVP2 item rather than a silently-dropped one. **Decided: option 2.** At pilot scale (spec §18.5–18.6: 8-week pilot, low order volume) a second PSP integration is speculative engineering, not a pilot-blocking need — but the gap must not quietly disappear from tracking.
- **This supersedes spec §20.2's mitigation entry for "Ödeme sağlayıcı kesintisi" for MVP1:** the mitigation is *not* "Stripe + PayPal çift entegrasyon" (impossible for this company) and is *not yet* any dual-provider pattern — for MVP1 the accepted mitigation is simply "single point of failure, accepted risk, iyzico's own uptime SLA is the only backstop."
- **This adds a new item to spec §18.7's MVP2 backlog** (which currently only lists route optimization, auto-assignment, multi-currency/B2B expansion): **PayTR as a secondary payment provider + a real circuit-breaker pattern**, reinstating spec §20.2's original redundancy intent once pilot volume justifies the integration cost. Don't let this get lost — if ADIM 6 ships single-provider and this line isn't still here when MVP2 planning starts, that's a documentation failure, not an intentional re-decision.

## Order State Machine (apps/api/src/orders, src/sla) — spec §2.3/§21.2/§17

The full chain from spec §21.2 is implemented: `draft → pending_payment → confirmed → assigned → in_progress → completed_pending_approval → closed | disputed`, plus the side branches (`pending_payment → cancelled` after 24h unpaid, `completed_pending_approval → disputed` on complaint).

- **`assigned → in_progress` (`POST /orders/:id/start`) is a filled spec gap, not an invention.** Spec §5's endpoint table has no route for this transition, but spec §2.3 madde 5 and §12.1 madde 27 (the PWA's "Başla" button) both describe it as a real product step, and spec §21.2's state machine includes `in_progress` as a real state — a literal implementation of the state machine needs *some* way to reach it. `OrdersService.addEvidence` and `.complete` were tightened to require `status === 'in_progress'` (previously unchecked) to make the chain actually enforced end-to-end, not just documented.
- **`completed_pending_approval → disputed`**: `OrdersService.addComplaint` now transitions the order when a complaint is raised while it's in that specific status (matching spec §21.2's literal edge) — complaints on orders in other statuses still get recorded, just without the status transition, since spec doesn't define that edge.
- **`disputed → refunded | reservice → closed` — partially resolved (Admin Panel ADIM 9, Phase 6).** `rejected` and `refunded` (via a real iyzico refund call) both work now — see the Şikayet Yönetimi section below. **`reservice` still has no real transition**, deliberately: actually re-dispatching a field partner to redo the work is a genuine, separate operational flow that doesn't exist yet; a complaint can be marked `resolved_reservice` but the order stays `disputed` until that real flow is built — not silently faked as `closed`.
- **SLA automation uses BullMQ** (`src/sla`), per spec §2.2's explicit architecture choice ("Message Queue (BullMQ + Redis)... otomasyon SLA takipleri") — not a simpler `@nestjs/schedule` substitute, even though that would've been less code. Three repeatable jobs, business logic factored into `SlaService` (plain, directly testable) with `SlaProcessor` (a thin BullMQ `WorkerHost`) just invoking it on schedule:
  - `cancelUnpaidOrders` — every 15 min, `pending_payment` orders past 24h → `cancelled` (spec §7.1 madde 12).
  - `autoCloseApprovedOrders` — every 15 min, `completed_pending_approval` orders past `approvalDeadline` → `closed` + payout record (spec §2.3 madde 7/§17). 15-min cadence for both is a guess — spec doesn't state a check interval for either window, only the 30-min assignment SLA's "her 5 dk" is explicit.
  - `escalateOverdueAssignments` — every 5 min (spec §17's literal interval), `confirmed` orders unassigned past 30 min → queues a `Notification` row per ops_manager user (not actual SMS/email/WhatsApp dispatch — that's ADIM 8; this only detects and records the *intent* to notify, deduped so re-sweeps don't spam).
  - **Field-naming caveat, not a spec-given guarantee:** neither the 24h payment window nor the 30-min assignment window has a dedicated timestamp field in spec §4.4 (`assigned_at` only fires once an assignment actually happens, which is exactly what's absent in the unassigned case spec §17 describes). Both sweeps use `updated_at` as a proxy for "when did this order enter the status being timed" — reasonable since normally nothing else touches the row in between, but not a field spec explicitly named for this purpose.
- **BullMQ's own connection is deliberately separate from the shared `REDIS_CLIENT`** (`src/redis`) used by auth/idempotency. BullMQ Workers require the underlying ioredis connection to have `maxRetriesPerRequest: null`; the shared client doesn't have that, and reusing it would throw at runtime. `SlaModule` builds its own connection from `REDIS_URL`, with a short `connectTimeout` and a `retryStrategy` that gives up after one failed attempt — deliberately, so that when Redis is unreachable (this sandbox, and every e2e test — none of them have a real Redis) the app still boots instead of hanging forever retrying. `SlaModule.onModuleInit` wraps its job-scheduling calls in try/catch and logs a warning rather than crashing app startup on a Redis hiccup.
- **⚠️ Not verified against a real Redis** — same standing caveat as Auth's Redis usage. `SlaService`'s business logic (the three sweep methods) is fully tested against real Postgres in `test/sla.e2e-spec.ts` by calling them directly; the BullMQ scheduling/cron-trigger machinery itself is only confirmed to not crash app boot (verified by running the built app against real Postgres with no Redis available), not confirmed to actually fire jobs on schedule against a live queue.
- **Debugging note if you write more time-based tests:** don't pass a JS `Date` as a `$executeRaw` parameter to backdate a `timestamp(3)` (no timezone) column for test setup. The write path applies an implicit database-session-timezone conversion that Prisma's normal ORM read path doesn't reverse — on a non-UTC session timezone (this sandbox's embedded Postgres defaults to `Europe/Istanbul`) this silently introduces a wrong-by-the-UTC-offset skew. `test/sla.e2e-spec.ts`'s `backdateUpdatedAt` helper works around it by formatting an explicit UTC string literal (`'YYYY-MM-DD HH:MI:SS.sss'::timestamp`) instead of binding a Date parameter — copy that pattern, not the naive one.

## Evidence verification system (apps/api/src/orders, src/storage, spec §8) — ADIM 7, implemented

Design decisions locked in during planning, followed as-is during implementation:

- **Object storage: AWS S3 (`eu-central-1`), not DigitalOcean Spaces.** Spec §8.2 requires 2-year WORM retention on evidence photos. DigitalOcean Spaces does not support Object Lock/WORM at all (confirmed via research) — disqualifying regardless of cost/simplicity advantages. S3 Object Lock (Compliance mode) is the intended mechanism, at no extra charge. CDN via CloudFront in front of the bucket (not yet configured — `EVIDENCE_CDN_BASE_URL` falls back to a raw S3 URL until then). Lock is intended for the *original* uploaded photo only — the CDN-served compressed derivative (spec §8.2) is regenerable, doesn't need its own lock.
  - **✅ Object Lock confirmed active (previously an open finding, now resolved) — but it required a real code fix, not just a bucket-config change.** After the user configured the bucket's default Object Lock retention rule (2yr, Compliance) in the AWS console, the *exact same* presigned-upload flow that worked before started failing live with `400 InvalidRequest: Content-MD5 OR x-amz-checksum- HTTP header is required for Put Object requests with Object Lock parameters` — this error class only appears on Object-Lock-enabled buckets, so it is itself strong independent confirmation the default rule is now genuinely active (the earlier `ObjectLockMode: undefined` symptom was, as suspected, simply "no default rule configured yet," not a code bug).
    - **Root cause**: S3 mandates a content-integrity header (`Content-MD5` or `x-amz-checksum-*`) on every `PutObject` to an Object-Lock-enabled bucket. For a *presigned* URL specifically, that header's value must be baked into the signature at presign time (SigV4) — the server can't just declare "some checksum is required" and let the client supply any value later; the exact checksum has to be known before signing, or S3 rejects it as `SignatureDoesNotMatch`.
    - **Fix, live-verified**: `StorageService.createPresignedUploadUrl(key, contentType, contentSha256)` now takes a caller-supplied `contentSha256` (base64 SHA-256 of the exact file bytes) and bakes it into the `PutObjectCommand` via `ChecksumAlgorithm: 'SHA256'` + `ChecksumSHA256: contentSha256`, and passes `unhoistableHeaders: new Set(['x-amz-checksum-sha256'])` to `getSignedUrl` so the checksum is a required *signed header*, not hoisted into the query string (a hoisted/query-string-only checksum was tried and still failed — S3's Object Lock integrity check only honors the real header). **New API contract, propagated end-to-end**: `POST /orders/:id/evidence/upload-url` now requires a JSON body `{contentSha256}` (`CreateEvidenceUploadUrlDto`, base64, exactly 44 chars) — the caller must hash the file locally *before* requesting the upload URL, then send that same value both to this endpoint and as the `x-amz-checksum-sha256` header on the actual `PUT`. **This is a real, load-bearing requirement for the field-partner PWA (ADIM 8)**: it must compute `crypto.subtle.digest('SHA-256', fileBytes)` (built into browsers, no extra library) client-side before calling this endpoint.
    - **✅ Directly verified, not inferred — Object Lock is real and correctly configured.** After the user added `s3:GetObjectRetention` to `guzelkabir-api`'s IAM policy, a live `HeadObject` on the test object returned `ObjectLockMode: "COMPLIANCE"` and `ObjectLockRetainUntilDate: 2028-08-27T11:49:59.792Z` — exactly ~2 years from the object's `LastModified` (`2026-08-27T11:50:00.000Z`). This supersedes the earlier checksum-error-based indirect inference with direct proof: spec §8.2's WORM requirement is genuinely active on `guzelkabir-evidence-prod`.
    - `MockStorageService.createPresignedUploadUrl` (e2e test double) accepts and ignores the extra params — real checksum verification isn't meaningful against an in-memory mock.
  - **⚠️ Process failure, corrected: live S3 verification must never write real test data into the production bucket again.** The checksum-fix re-verification above wrote a real object into `guzelkabir-evidence-prod` — unacceptable, since that bucket is meant to hold only real customer evidence photos under 2-year WORM retention, not throwaway test artifacts. **Standing rule now in effect**: all live S3/Object-Lock verification targets a separate bucket, `S3_EVIDENCE_STAGING_BUCKET` (env var now set — the user provisioned `guzelkabir-evidence-staging`, same Object Lock settings as prod, added to `apps/api/.env`; placeholder already in `.env.example`) — never `S3_EVIDENCE_BUCKET` for anything that isn't a real order's evidence photo. The `HeadObject` verification above was **the last read-only touch to the prod bucket** — no further writes were made there; any future S3 live-testing (ADIM 8's field PWA, etc.) must go through the staging bucket instead.
  - **Known test artifacts left in the prod bucket — exact inventory, so nobody has to re-investigate this later:**
    - `evidence/_checksum-fix-verification/54c2e291-7e47-464a-829b-b0228e5c9a96.txt` — a small text object (not a real photo), created **2026-08-27T11:50:00.000Z**. Confirmed 2-year Compliance retention, eligible for deletion at **2028-08-27T11:49:59.792Z**. Cannot be deleted early, by design.
    - `evidence/_presign-probe/` and `evidence/_object-lock-probe/` — two prefixes from an earlier debugging session; exact keys/timestamps were never recorded and can't be enumerated from application code (`guzelkabir-api` has no `s3:ListBucket`, confirmed via a live `AccessDenied`). Check the S3 console directly if a full count under these two prefixes is ever needed.
- **Geotag tolerance is per-cemetery**: `Cemetery.geotagToleranceM` (nullable `Int`, migration `20260101000007`), falls back to `GEOTAG_DEFAULT_TOLERANCE_M` (env, default 150) when `NULL`. `PATCH /cemeteries/:id` (`ops_manager`/`admin`, spec §5's table doesn't have this route — user decision) added so the column is actually reachable, not DB-only.
- **Missing reference coordinate on `grave_locations`** (the "yardım isteyin" flow from ADIM 5): evidence upload is **not blocked** — falls to `manual_review` with an Ops notification explaining why, keeping the field partner's flow uninterrupted.
- **Ops manual-review notification reuses `SlaService.escalateOverdueAssignments`'s exact pattern** — a queued `Notification` row (`templateKey: 'evidence_manual_review'`), no real dispatch (ADIM 8/9's job). Triggered for all three failure outcomes (`missing_exif`, `gps_mismatch`, `timestamp_mismatch`) plus the no-reference-coordinate case — spec §8.1 madde 17 only explicitly names the first two, `timestamp_mismatch` and the missing-reference case were included for consistency, a small flagged extension.
- **"Yalnızca canlı çekim" (spec §8.1 madde 13) — confirmed as a UI-only, backend-unenforceable constraint, documented as an accepted MVP1 trust boundary.** Backend's real levers: EXIF-timestamp freshness (>24h, madde 18) and GPS/Haversine — deterrents, not live-capture proof.
- **⚠️ KVKK erasure vs. WORM retention legal tension — flagged for spec §19's "Güvenlik/Uyumluluk Danışmanı" role, not resolved in code.** No code path promises unconditional deletion of evidence photos on a KVKK erasure request.

**Implementation** (`src/storage` + `src/orders`): `POST /orders/:id/evidence/upload-url` (new) issues a real S3 presigned PUT URL (`@aws-sdk/s3-request-presigner`, 5-min TTL) scoped to `evidence/{orderId}/{uuid}.jpg`. `POST /orders/:id/evidence`'s DTO no longer accepts `exifGpsLat`/`exifGpsLng`/`exifTimestamp` from the client (trusting those defeated the entire point) — instead `OrdersService.addEvidence` downloads the real object from S3, extracts real EXIF via `exifr.parse()` (`src/orders/evidence-geo.util.ts` — pure, unit-tested functions for `extractExifData`/`haversineDistanceMeters`/`resolveGeotagStatus`), generates a compressed CDN derivative via `sharp`, computes Haversine against `grave_locations`' reference coordinate, and writes the real `geotag_validation_status`.

## Field partner PWA offline-first (apps/field-pwa) — ADIM 8b, implemented

spec §12.2: task list/detail viewable offline, evidence photos captured offline queue locally and upload once connectivity returns. Sequencing was explicit user decision after ADIM 8: do this before Admin Panel, since Admin Panel is its own full sprint (spec §18.3) — see the field-partner onboarding→active gap tracked in the API Layer section, still unresolved, waiting on that dedicated ADIM.

**Architecture — one unified action queue, not three separate ones:**
- `src/lib/db.ts` — `idb`-wrapped IndexedDB, single `pendingActions` store covering `start`/`evidence`/`complete`, each record has `status: pending|syncing|synced|failed` and a monotonic `seq`.
- `src/lib/queue.ts` — `enqueueAction` writes and immediately attempts a sync; `flushOrder` processes one order's actions strictly in `seq` order (evidence never fires before `start` synced, `complete` never fires before both evidence photos synced — the backend would reject out-of-order anyway, this just skips the wasted round-trip); `flushQueue` drives every order with pending items.
- `src/sw.ts` (vite-plugin-pwa, `injectManifest` strategy — chosen over `generateSW` specifically because custom Background Sync logic is needed): `precacheAndRoute` for the app shell, `NetworkFirst` for task-list/detail GETs (spec §12.2's offline-viewable requirement), and a `sync` event listener invoking the same `flushQueue()`.
- **Idempotency-Key reuse, not new infra**: each queue item's own UUID is sent as `Idempotency-Key` on `start`/`evidence`/`complete` — `OrdersController` got `@Idempotent()` added to those three routes specifically to make retries of an interrupted request safe (spec §5.1's interceptor already existed, just wasn't applied there). If the first attempt actually reached the server, a retry replays the cached response instead of double-executing.
- **Conflict handling is server-authoritative, never silently overwritten**: a `409` (idempotency lock still processing) retries later automatically; any other `ApiError` (4xx) is a permanent rejection → status `failed`, the server's own message shown to the user, never auto-retried; a network-level failure (not an `ApiError`) leaves the item `pending` for the next sync attempt. Literal implementation of spec §12.2's "son yazan kazanır, sessizce ezilmez."

**Real bugs found via live Playwright testing (`context.setOffline(true)`, per explicit user instruction — verified, not just assumed to work):**
- **Missing SPA offline-navigation fallback.** `precacheAndRoute` alone only matches exact precached URLs, not client-routed deep links (e.g. `/gorevler/:id/fotograf`). Without a `NavigationRoute`, offline navigation to a non-precached path showed Chromium's native offline error page — the app never loaded, so the IndexedDB queue looked inaccessible (not lost, just unreachable). Fixed: `registerRoute(new NavigationRoute(createHandlerBoundToURL("/index.html")))`.
- **⚠️ Real, load-bearing finding: the browser `online` DOM event alone is not a reliable-enough reconnect trigger.** Reproduced deterministically: when `context.setOffline(true)` is set on a *fresh* browser context before its first navigation, and that navigation is served offline via the Service Worker's precache fallback, `navigator.onLine` gets stuck reporting `true` for the rest of that session — even though real network requests genuinely fail (`net::ERR_INTERNET_DISCONNECTED`, confirmed). Later going back online produces no `false→true` transition, so `online` never fires. Isolated minimal repros confirmed the event fires correctly in every other tested ordering (a plain new context; a persistent context where offline is toggled only after the page is already interactive) — this is specific to "offline set before first paint on a fresh context." Whether this is a pure Playwright/CDP timing artifact or a real edge case a field partner could hit on a real device with flaky cemetery signal wasn't conclusively distinguished — and given the actual use case (outdoor, intermittent connectivity), it wasn't worth gambling on either way. **Fix, not a test-only workaround:** `queue.ts` now also exports `startPeriodicSync()` — a plain 20s `setInterval` calling `flushQueue()`, wired up in `main.tsx` alongside the existing `online` listener and Background Sync registration. Three independent reconnect triggers now, not one.
- **Cross-context auth** (found and fixed earlier in this same ADIM): the Service Worker and the page are separate JS module instances, each with its own in-memory access-token copy (`api.ts` bundled twice). `flushQueue()` proactively calls `refreshAccessToken()` when no in-memory token exists, relying on the shared httpOnly refresh cookie sent automatically in either context — not assuming the page's own token state.
- **Separate TypeScript project for the Service Worker**: `sw.ts` needs the `WebWorker` lib, the app needs `DOM` — can't mix in one tsconfig. Solved with `tsconfig.sw.json` (project reference) + `tsconfig.app.json` excluding `sw.ts`, plus hand-written ambient types for the Background Sync API (`background-sync.d.ts`, not yet in TypeScript's built-in DOM lib).
- **Test against `vite preview` (production build), not `vite dev`** — dev-mode SW registration did not reliably reproduce production offline-navigation behavior even after the `NavigationRoute` fix.

**The exact scenario requested — verified for real, all four phases passing:** go offline → capture a photo (real `enqueueAction`, real IndexedDB write) → force the record to `syncing` (simulating a request killed mid-flight) → close the entire browser context → relaunch on the same profile, still offline → confirm the record survived and was reset from `syncing` back to `pending` (`resetInterruptedSyncs()`, called before `flushQueue()` on every boot — order matters, a fresh `flushQueue()` would otherwise skip records still marked `syncing` and never retry them) → go online → confirm it actually flushes to `synced`. Verified against a live `apps/api` (real Postgres) and the real `guzelkabir-evidence-staging` bucket — the evidence row landed with a real `file_url` pointing at staging, confirmed via a direct DB query (`geotag_validation_status: "missing_exif"`, expected: fake camera device, no real EXIF GPS, same code path as ADIM 8). Real sync latency (S3 round-trip from this sandbox) meant waiting up to ~40s in testing, not instant — expected, not a bug.

**Not verified, real remaining gap:** Background Sync itself (the `sync` event firing in a real browser process on real reconnect, independent of the page being open) could not be directly confirmed in this headless-Chromium sandbox — only the periodic-poll and `online`-event fallbacks are proven to work here. Background Sync also has zero Safari/iOS support, so the periodic-poll fallback is the one universal guarantee across browsers, not just a backstop. Revisit if a real Android field test ever becomes possible.

## Conventions — follow these
- **apps/web styling stays in the single global stylesheet `apps/web/src/app/globals.css`.** No CSS Modules, no Tailwind in apps/web. The original designer's class names are preserved verbatim for fidelity — match existing class names, token names, and section comments when adding UI. This does **not** apply to `apps/admin`/`apps/field-pwa` (not yet scaffolded) — those follow spec §3 (Tailwind + shadcn/ui) since they have no pre-existing approved design to preserve.
- **Design tokens** are CSS custom properties in `:root` (only the "C · Modern Sakin" theme; A/B themes and the theme switcher were intentionally removed). Derive colors with `color-mix(in srgb, …)`.
- **Photos are CSS `background-image`** (`.ba-before`, `.ba-after`, `.hero-photo`), not `<img>`. Swap by editing the `url(...)` in `globals.css` or replacing the file in `apps/web/public/`.
- **Currency:** amounts are `{ try: number, eur: number }` pairs rendered via `<Price>` / `useCurrency().fmt`; the ₺/€ toggle is still display-only (no FX) — the wizard's actual `POST /payments/intent` call does send the selected currency to iyzico now (see Payment provider section), but real daily-FX-synced *pricing* (spec §7.3) needs iyzico's paid Multi Currency add-on enabled first, not done yet.
- **Client vs server:** pages are server components using client "islands" where interactivity/context is needed. The wizard and panel are full client components. `useCurrency()` must run inside `<CurrencyProvider>` (provided in `layout.tsx`).
- **Copy is final Turkish** — don't paraphrase existing strings. Components are structured so i18n can be layered in later without a rewrite.
- **apps/api** endpoints must match spec §5's method/path/role table exactly — don't invent naming.

## Workflow
- Run `npm run build` (root, via Turborepo) after changes — apps/web is statically prerendered, so type/build errors surface immediately. Keep Next ≥ 15.5.x (past vulnerable-version issues).
- For visual changes, verify in a browser preview (screenshot + console check) instead of assuming — this caught a dropped CSS rule during the initial build.
- This repo (`mertasln/guzelkabir-app`) currently has no hosting/deploy integration set up — no Vercel or otherwise.
- **Commit at the end of every ADIM, right after the user approves it — standard step, not optional.** Never push (the user pushes manually). This rule exists because ADIM 2 through 8b were built without ever being committed — only the initial prototype commit existed in history until a single large catch-up commit was made afterward. Don't let that gap happen again: one commit per approved ADIM, with a message that actually describes what that ADIM did (not just "wip"/"update").
